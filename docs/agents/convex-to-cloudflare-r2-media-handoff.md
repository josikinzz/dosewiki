## Recommended target design

Keep the split simple:

- Convex remains the source of truth for replication records, taxonomy, artist attribution, rights, dates, subjective-effect tags, ordering, and editorial state.
- R2 stores only immutable media bytes under their SHA-256 keys.
- Convex stores R2 object keys, not Cloudflare credentials and preferably not hard-coded hostnames.
- One central resolver converts object keys into public delivery URLs.

Because the bucket is private, decide and configure the delivery surface before changing database rows. For a public media gallery, prefer a stable Cloudflare custom domain or a narrowly scoped Worker in front of the private bucket. Do not expose S3 API credentials to the browser. Avoid per-request expiring signatures if stable cacheable public media URLs meet the rights/access model; if access control is required, use a Worker or server-side signer and document URL lifetime and caching behavior.

Use immutable cache headers for content-addressed keys, correct `Content-Type`, and byte-range support for video. Confirm `Content-Disposition` does not force downloads. If a custom hostname is used, keep it in one server-side environment variable such as `REPLICATION_MEDIA_BASE_URL`; do not bake it into every row.

## Data model migration

Add R2 fields without removing the existing Convex Storage fields. A direct, explicit model is easiest to audit:

- `r2_key`
- `thumbnail_r2_key`
- `preview_r2_key`
- `motion_r2_key`
- `motion_poster_r2_key`

All should initially be optional. Retain `storage_id`, all rendition storage IDs, `url`, and `thumbnail_url` as rollback sources.

Update `resolveReplicationUrls` to use this precedence during migration:

1. Valid R2 key plus configured delivery base URL.
2. Existing Convex Storage ID through `ctx.storage.getUrl`.
3. Existing direct URL fallback where the current resolver already permits one.

Do not silently invent direct fallbacks for preview or motion variants without tests; current behavior deliberately omits them. Reject malformed keys, path traversal, and keys outside `media/sha256/`. Keep the URL construction server-side and deterministic.

Using the existing `url` field alone is possible for main media, but it cannot cleanly represent every rendition and couples rows to a hostname. Explicit R2 key fields preserve provenance and make hostname changes cheap.

## Reconciliation ledger: measure twice

The R2 manifest proves bytes are present; it does not by itself prove which R2 object belongs to every live production field. Build a dry-run mapping ledger before any Convex mutation.

For every production replication and each of its five possible media fields, record:

- Convex replication ID and slug
- variant role (`main`, `thumbnail`, `preview`, `motion`, or `motion_poster`)
- old Convex storage ID or direct URL
- resolved source URL status
- measured source byte length and SHA-256
- matching R2 key and manifest record
- match status: `exact`, `missing`, `ambiguous`, or `error`
- proposed patch and verification status

Derive SHA-256 from the actual currently served bytes or a previously verified production upload ledger. Do not match by filename, slug, title, dimensions, perceptual hash, or approximate file size when changing a production URL. Perceptual matching is review evidence, not identity proof.

Require exactly one byte-identical R2 object for every field selected for migration. Leave unmatched or ambiguous fields on Convex and report them visibly. Save the ledger in a resumable JSON/JSONL artifact with no secrets. Check it before every retry.

## Execution sequence

1. Run `npm run convex:doctor`; explicitly verify `TARGET_CONVEX_URL` is production `glad-minnow-656` before any write.
2. Configure the public/custom R2 delivery hostname or Worker and validate a representative image, GIF, video, poster, preview, and motion pair directly from that hostname.
3. Build and review the read-only SHA mapping ledger against live production rows and the verified R2 manifest.
4. Add optional R2 fields, validators, typed reads/writes, central URL resolution, tests, and environment documentation. Preserve all old fields.
5. Deploy code capable of dual-read behavior before populating any R2 keys.
6. Canary a small, reversible set covering image, GIF-like motion, video, poster, preview, and motion variants. Record old values and expected R2 keys in the ledger.
7. Invalidate relevant Convex/Next caches, rebuild affected public routes, and verify served HTML and media requests on both Dose Wiki and Effect Index surfaces.
8. Expand in bounded batches. After every batch, compare database rows with the ledger and verify HTTP status, content type, content length, range requests, playback/decoding, and expected SHA where feasible.
9. Run a final complete reconciliation: every selected field must be R2-backed or explicitly reported as a retained Convex exception.
10. Stop after the URL cutover is verified. Removal of old Convex Storage objects is a separate destructive project requiring a fresh inventory, rollback window, and explicit authorization.

## Canary and acceptance checks

The canary is complete only when all of these pass:

- Image and poster decode in the browser.
- GIFs remain animated; GIF-like motion pairs preserve intended poster/motion behavior.
- Videos play, seek via HTTP range requests, retain audio where expected, and report the intended codec/dimensions/duration.
- `url`, `thumbnail_url`, `preview_url`, `motion_url`, and `motion_poster_url` resolve to the expected R2 delivery hostname for migrated variants.
- Cache headers are public and immutable only for content-addressed keys.
- No Cloudflare credentials appear in client bundles, Convex rows, logs, HTML, reports, or Git history.
- Public replication detail pages, galleries, artist pages, substance galleries, featured Effect Index content, and Replication Studio thumbnails/previews work.
- Both application flavors and their production hosts are checked according to `docs/agents/deployment.md`.
- Served HTML contains the expected R2 URLs after cache invalidation/rebuild; a successful mutation or deployment alone is not completion.
- The API shape documented in `src/app/api/v1/openapi.json/route.ts` remains compatible.

Run repository verification appropriate to the change. Because this touches Convex and the application, the expected gate is `npm run verify:all`, plus focused resolver, gallery, viewer, studio, CSP, and media delivery tests. Follow any stricter current instructions in `AGENTS.md`.

## Rollback

Rollback must remain possible without restoring bytes:

- Keep all old Convex storage IDs and direct URLs during migration.
- Make the resolver precedence switch reversible with a server-side flag or a small code rollback.
- Record every changed row and its old values in the ledger.
- If the R2 delivery hostname, Worker, or a media class fails, disable R2-first resolution and fall back to Convex immediately.
- Do not delete Convex media until the owner separately approves it after a stable observation window and an exact retained-object inventory.

## Security and operational boundaries

- Never commit the R2 token, S3 endpoint credentials, rclone configuration, Convex deploy key, or Cloudflare account secrets.
- Use scoped credentials and environment variables. Browser code gets public media URLs only.
- Treat Convex mutations and deployment changes as production writes. Use dry run, canary, ledger, explicit production target, and read-back verification.
- Do not rewrite rights status or imply permission merely because an asset is publicly served.
- Do not modify, move, transcode, or delete the immutable source media held by the Dose Wiki Media Review archive.
- Keep unmatched, excluded, unclear, collision-gated, and artist-review records visible.
